### 1.4 现状的问题（按影响排序）

1. **"这道题怎么处理"被决定了 9 次。** 理解阶段没有交出一个最终计划，后面每个阶段都可以改判。要回答"为什么这道题走了名单路线"，得把 [判断 2]、[判断 3]、[判断 7] 合起来看。现在只有名单这一项写进了运行记录（`list_decision`）。
2. **证据路线是"函数里套着一条流水线"。** 382 行里包含 6 个步骤和 4 种名单变体，步骤之间只靠注释分隔。单库和两库的名单各实现了一遍，前两天加的分流也接了两遍。
3. **三套入口并存。** 旧路径、研究代理、意图解析由环境变量切换，`_answer_legacy` 里还有一套自己的题型判断。
4. **补救逻辑分散。** 联网补充在 [判断 4]、[判断 5]、[判断 9] 三处都可能触发，各自的条件不同。
5. **阶段之间的约定没有写进代码。** 字典字段可有可无，失败原因是自由文本。

## 2. 目标

### 2.1 流程图

```
提问
│
├─ 0. 入口：长度、限流、预算（限流计数放进数据库，见第 4 节第 5 步）
│
├─ 1. 理解问题 → 产出唯一的"处理计划" QuestionPlan
│     正则标签 + 研究代理的工具结果，只在这里合并
│     判断依据写进 plan.reasons
│
├─ 2. 取证（按 plan.route 和 plan.shape）
│     statistics / metadata / records / claims：直接读库
│     evidence：检索候选（一个或两个集合，用同一个函数循环）
│
├─ 3. 作答（按 plan.shape）
│     list：标准 → 分流 → 筛查 → 三组（只实现一遍）
│     answer：生成 + 逐字核对
│     table：统计结果
│
├─ 4. 核对与补救
│     核对失败 → 写明原因（用固定的原因代码）
│     plan.allow_web 为真且馆藏答不出 → 联网补充（只在这里）
│
└─ 5. 记录：计划 + 每个阶段的结果和花费，写进运行记录
```

规则只有一条：**后面的阶段只读计划，不再读原始问题。** 原始问题只用于作答时的措辞和语言。

### 2.2 处理计划 QuestionPlan（建议的字段）

| 字段 | 含义 | 现在在哪里决定 |
|---|---|---|
| `route` | statistics / metadata / records / claims / evidence / clarify / limited | 研究代理最后调用的工具 |
| `shape` | list / answer / table | [判断 7]：正则 或 模型 |
| `list_kind` | screen / relation / literal（只在名单题时有） | [判断 7] 的细分 |
| `datasets` | native / social / 两者 | filters 和 [判断 7] |
| `filters` | 收窄后的范围（只能比用户原来的小） | 研究代理 + `narrow()` |
| `search_query` | 检索词（英文） | 研究代理 |
| `allow_web` | 答不出时能否联网 | [判断 5]、[判断 9] 的正则 |
| `clarify_message` | 需要澄清时问用户什么 | 研究代理 |
| `reasons` | 每一项是怎么决定的（规则命中、模型声明、默认） | 现在没有统一记录 |

### 2.3 每个阶段的约定

| 阶段 | 输入 | 输出 | 不做什么 |
|---|---|---|---|
| 理解 | 问题、用户范围 | QuestionPlan | 不检索作答用的证据 |
| 取证 | QuestionPlan | 证据集合（含覆盖了多少条记录） | 不判断题型 |
| 作答 | QuestionPlan + 证据 | 草稿答案 + 花费 | 不联网、不改范围 |
| 核对与补救 | 草稿答案 + QuestionPlan | 最终答案 + 原因代码 | 不重新判断题型 |
| 记录 | 以上全部 | 运行记录 | — |

## 3. 不变的部分

下面这些在现状里是对的，目标里保留原样：

- 模型给的范围只能缩小，不能扩大（`narrow()`）。
- 引文只能从给定段落里挑，并且在服务器上逐字核对。
- 每个阶段前后检查数据版本，数据变了就不发布答案。
- 理解阶段查到的段落不直接用于作答。
- 付费调用先预留、后结算。

## 4. 建议的改法（分步，每步都能单独验证、单独回退）

1. **先只加计划，不改行为。** 在 `_answer_with_tools` 里把现在分散的判断汇总成 QuestionPlan 写进运行记录，原来的逻辑照旧运行。用现有测试和几道真实问题核对：计划里写的路线，和实际走的路线是否一致。
   *进度（2026-10-26）：已做。`question_plan.py` 生成计划，运行记录多了 `question_plan` 和 `plan_check` 两个键（后者在联网兜底之后写，推不出的项记 None）。真实问题的对照还没跑。*
2. **证据路线改为读计划。** `_answer_evidence` 不再调用 `question_contract` 和正则，改从计划里读形态和是否允许联网。每改一项，跑一次相关测试。
3. **名单题只实现一遍。** 把单库和两库合成"对每个集合循环"的一个函数，分流只接一次。用人工标注集的 5 道题重跑一遍，对照三组的结果（约 $0.08）。
4. **补救只留一处。** 把三处联网补充的条件合并到第 4 阶段，条件由 `plan.allow_web` 决定。
5. **原因代码固定下来。** 把失败原因从自由文本改成固定的代码表，限流计数移进数据库。
6. **入口只留一套。** 删掉旧路径，或者把它改成同一计划下的一个模式。等前 5 步稳定以后再做。

每一步都会单独提交。
