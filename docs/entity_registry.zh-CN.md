# 实体表（组织身份层）

更新：2026-10-08。状态：**AI 提议，尚无具名人工审核**。

## 解决什么问题

来源数据里，同一组织在不同位置写法不同：原生广告写 `exxonmobil`，社交帖子写 `ExxonMobil`；原生写 `api`，社交写 “American Petroleum Institute (API)”；`statoil` 在 2018 年更名为 Equinor；`williams`、`williams companies`、“the williams companies, inc.” 是同一家公司。没有统一身份时，跨集合按公司筛选会漏掉一半，图谱里同一组织也会显示成好几个节点。

实体表把这些原始写法挂到同一个组织上。**原始数据一个字都不改**：查询时按组织展开成它在当前范围内的所有原始写法，再用原始写法筛选。

## 文件

- [`src/observatory/entity_registry.v1.json`](../src/observatory/entity_registry.v1.json)：118 个组织（公司 101、行业协会 16、活动 1）和 8 个媒体。每个组织有稳定 ID、名称、类型、别名（含中文）、曾用名、各集合的原始写法、合并依据和审核状态。
- [`src/observatory/entities.py`](../src/observatory/entities.py)：加载并校验实体表，提供查找、展开和“问题里是否提到这个组织”的判断。

加载时会做以下校验，任何一条不通过都直接报错：
- 组织 ID 重复；
- 同一原始写法同时属于两个组织；
- 同一别名同时指向两个组织；
- 组织类型不在规定的取值范围内。

实体表内容一旦改动，版本号（`entity-registry-v1:<哈希>`）也会随之改变。

## 规则

1. **只合并登记过的写法。** 名称、别名、曾用名可以用来查找组织，但真正合并的只有实体表明确列出的原始写法。名字相似但未登记的来源值（例如测试里的 “williams plumbing”）仍然要求用户澄清。
2. **不扩大已有选择。** 用户已在筛选里明确选了某种写法时，展开结果只保留已选的写法。
3. **两个集合分开报告。** 原生文章和社交帖子单位不同，统计永远分集合报告，不相加。
4. **可追溯。** 每次按组织展开，都会在 `alias_resolutions` 里记录组织 ID、类型、审核状态和实体表版本。
5. **短缩写区分大小写。** 判断问题是否提到某组织时，英文按词边界匹配；4 个字符以内的全大写缩写（BP、API、XOM）必须大小写一致，所以 “total number” 不会被当成 TotalEnergies，“bpm” 也不会被当成 BP。中文别名直接匹配。

## 接入位置

| 位置 | 作用 | 状态 |
|---|---|---|
| 规则规划器和共用别名函数 `structured_queries` | 别名、中文名、曾用名都能识别；同一组织的多种写法一起筛选 | 已接入 |
| 研究工具 `research_tools`：统计、检索筛选、`resolve_entity` | 按组织展开写法；候选标注所属组织 | 已接入 |
| 问题策略 `question_policy` | 通过共用别名函数自动获得实体表的别名 | 已接入 |
| 问题理解 `question_intent`（Codex P57） | 赞助方／媒体核对复用登记名称、别名与曾用名；其他维度仍核对字面依据 | 已在本机源码接入并做独立工程检查；该入口默认关闭，未部署 |
| 图谱 `knowledge_graph` | 新增组织节点，以及“识别为组织”“识别为媒体”“补齐赞助方”三种关系 | 已接入 |
| 组织总览 `GET /api/knowledge-graph/organizations` | 列出全部组织，以及它在两个集合中的可计数记录数；社交独有的组织也在内 | 已接入 |

## 补齐和范围外记录

- **补齐 1 条**：原生里有 1 条记录没有赞助方，标题是 “Paid Program: CERAWeek Connection”，链接路径 `/ceraweek/` 与全部 41 条 `cera` 记录相同，因此补齐为 CERAWeek。这只能说明它和这场活动相关，不能证明谁付了钱。补齐值绑定这条记录当前的版本，**只在图谱的“补齐赞助方”关系里出现**。原始字段仍然是空的，SQL 筛选和统计都不使用它。
- **范围外 65 条**：社交里有 65 条帖子既没有公司也没有账号，帖子链接属于达美乐、Epic Games、NordVPN 等与化石能源无关的账号。实体表逐条列出了它们的记录、版本、帖子作者账号和依据。**目前它们仍然计入社交总数**；要不要从统计中排除，由客户和审核人决定。

## 需要别人决定的事

- **客户**：行业协会（API、AFPM 等 16 个）和活动（CERAWeek）要不要和公司一起计数。目前它们按各自类型单独列出。
- **具名审核人**：确认组织身份、更名和补齐依据。确认后才能把审核状态从 `ai_proposed` 改为已审核。

## 没有做的部分

- **图谱里的“文章 → 题目判断”关系**：现有的内容判断读取接口只在评测会话中开放，因为 Q01–Q24 是客户的留出验收题，接进生产图谱会破坏掩码；而且这些判断都还待人审。这条关系属于评测专用图谱还是生产审核，需要先定下来。
- **主张抽取**：按约定等研究问题需要时再做，并单独申请付费授权。
- **母子公司关系**：数据里没有依据，没有登记。
