1. 按 Dockerfile 构建镜像；
2. 部署前自动执行 `observatory migrate`，把所有未执行的数据库迁移应用到线上数据库；
3. 用 `/healthz` 检查服务是否正常；失败时最多重启 5 次。

## 2. 上线前必须决定的三件事

1. **迁移 0007 要不要上线数据库。** 分支里已经包含 `0007_integrity_constraints.sql`，内容是：
   - 记录与当前版本之间加复合外键；
   - 文本块与版本之间加复合外键；
   - 加一个触发器，禁止修改或删除记录版本。

   合并到 main 后，部署时会自动执行。可能的风险：
   - 线上有不满足外键的旧数据：迁移失败，这次部署中止，旧版本继续运行；
   - 线上有就地修改版本的写入流程：部署后这些写入会被拒绝。

   建议先按第 4 节第 3 步只读检查线上数据，没问题再上线。如果暂时不想上线 0007，就在合并前把这个文件从分支里拿掉，以后单独上线。
2. **单题费用会上升约 37%。** 客户 24 题平均每题从 $0.041 升到 $0.056，原因是每批 4 篇、补读全文、复核这三项。线上每月预算上限是 $100（`OBS_MONTHLY_BUDGET_USD`），按新单价大约能答 1,800 题，以前约 2,400 题。要么接受，要么提高预算。
3. **耗时会增加约 27%。** 客户 24 题总耗时从 31 分钟增加到 40 分钟，候选多的名单题最慢。前端会显示进度，但单题等待时间会变长。

## 4. 上线步骤

1. **备份线上数据库**：用 Railway 的备份或 `pg_dump` 做一份新备份（上一份 `railway-full-20261001-68b3.dump` 已经过时），记下校验值。
2. **开 PR**：`claude/rag-accuracy-20261015` → main，审阅改动。这次改动量很大，其中包括其他会话的代码，需要逐目录确认是否都要上线。
3. **只读检查 0007 的前提**（在线上数据库执行，只读）：
   - 当前版本不属于本记录的记录数；
   - 文本块的版本不属于本记录的块数；
   - 是否有代码路径会 UPDATE 或 DELETE `record_versions`。

   三项都为 0，或者确认没有这类写入，才合并；否则先把 0007 从分支里拿掉。
4. **合并到 main**：Railway 自动构建，执行 `observatory migrate`，然后做健康检查。选一个访问少的时段。
5. **上线后冒烟测试**：只用虚构问题或公开示例，不用客户题。检查以下几项：
   - `/healthz` 正常；
   - 名单题、内容题、统计题、库里没有答案的题各 1 道；
   - 回答开头写明了核对范围，没有“不符合／无法判断”的计数；
   - 费用账本有记录，单题费用和耗时在预期范围内。
6. **观察 1–3 天**：每天看单题费用、耗时、失败率（`service_unavailable`、`limited`），以及名单复核删除了多少（`verified_removed`）。

## 5. 回退方案

- **代码**：在 Railway 上重新部署上一个版本（`d33b256`），或者对合并提交做 `git revert` 再推送 main。
- **数据库**：0007 只新增约束、函数和触发器，不改数据。要回退时执行下面的 SQL，再删掉 `schema_migrations` 里版本 7 那一行：

  ```sql
  DROP TRIGGER IF EXISTS record_versions_no_update ON record_versions;
  DROP FUNCTION IF EXISTS record_versions_immutable();
  ALTER TABLE chunks DROP CONSTRAINT IF EXISTS chunks_record_version_fk;
  ALTER TABLE records DROP CONSTRAINT IF EXISTS records_current_version_fk;
  ```

  旧代码不依赖 0007，代码回退可以不回退数据库。
- **费用**：发现单题费用异常时，先调低 `OBS_MONTHLY_BUDGET_USD`，服务会按预算拒绝新请求，不会超支。
