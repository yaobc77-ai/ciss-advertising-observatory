## 二、先索要四类材料

不要求客户重新整理全库。优先请他们提供已有共享文件、原始导出和负责解释的人；缺什么就明确标缺失，由团队完成格式转换与初筛。

| 优先级／对象 | 向客户索要或确认 | 最小可用形式 | 解锁哪些测试 | 材料未到时我们继续做什么 |
|---|---|---|---|---|
| **P0：Ned，经 PM 协调** | 本期正式社交导出、字段说明、导出时间／范围、哪些帖子纳入“广告”；Miami 原型访问 | 现有 CSV/JSON 与原始字段表即可。若完整导出暂时不能提供，先给保留完整字段和缺失情况的代表样本，并约定完整导出的负责人／时间 | 社交导入、筛选统计、原帖和归档访问、社交 RAG、跨库查询与规模检查 | 用明确标记的夹具测试适配器；不把旧仓库 50 条研究样本作为本期广告验收库 |
| **P0：Michelle／数据负责人** | 指定当前应以哪份 native 表为准；确认计数、赞助方和日期口径 | 回复下节的简短选择／裁决即可；现有公司别名表、采集说明有则提供 | 公司×媒体统计、百分比分母、日期筛选、重复及多赞助方处理 | 程序对账、保留原字段和不确定状态；由团队准备争议样例，不让客户重做全库标注 |
| **P0：原生数据／归档负责人，经 PM 协调** | 原文、正文、截图／PDF／归档 URL 的对应清单，以及已知失效或缺失说明 | 已有清单中的 record ID 或原文 URL，加附件路径／共享链接／采集日期；没有完整清单时先提供明确对应的样例 | 原文失效后的回退、记录详情、附件是否对应正确广告、缺失正文的证据边界 | 继续核验本地候选和补来源回执；标题相似度不足以自动确认附件身份 |
| **P0：Michelle＋代表用户** | 真实研究问题、已知相关来源、领域审阅人 | 首轮建议 5–10 个实际问题、其中 2–3 个附熟悉的广告／帖子链接；指定至少一位领域审阅者 | 检索相关性、答案充分性、归属、限定条件、正确的无证据处理及易用性 | 团队先准备候选证据和答案评分表，客户核对内容；不要求客户从零写标准答案 |

社交导出需重点解释的字段：稳定帖子 ID、平台、账号、公司／母实体、正文、原帖链接、发布时间及时区、归档链接、付费／品牌内容标记及其证据来源。互动数须附统计时点。不存在的字段可以标未知；我们不会自动把账号名或 parent_entity 当成已核实付款方。

**无需再索要**：已提供的旧源码 ZIP、已掌握的原生表和 PDF 包、重复的 517 句历史标签。需要的是权威版本、映射和口径说明，而不是把相同文件再次打包。

## 三、客户需要裁决的具体问题

团队先给出当前处理和推荐选项，客户只需要确认或更正。

1. **计数单位。** 当前以来源记录／URL 为基础计数。相同广告在不同媒体、重复抓取、转载、多个赞助方分别如何计数？由团队准备具体重复样例，避免抽象争论。
2. **公司范围。** CERAWeek 这类活动，以及 API／AFPM 这类协会，是否与公司一起统计，还是单列组织类型？公司改名、母子公司是否合并？建议保留原实体与展示名，未经确认不合并。
3. **赞助方身份。** 旧代码中 16 条华邮 sponsor 与搜索词赋值策略一致。团队先整理披露证据；客户裁决证据不足时是否可作为“来源表所列 sponsor”展示，以及是否计入经过核验的公司统计。不能预先认定这 16 条都是错误。
4. **日期与百分比。** 日期不全是否保留 Unknown／月精度？以文章发布日期还是采集日期筛选？百分比按当前筛选集合、单家媒体还是其他分母展示？建议明确写出分母，采集日期不代替发布日期。
5. **回答目标。** 首轮以英语、广告内容研究和原文证据为主；对比／解释需要多详细？没有可用证据时，用户希望看到缺口说明还是澄清问题？广告提出的承诺应保留归属及“计划／预计／已实现”的区别。
6. **主题和标签。** 是否接受当前历史自动标签作为带限制说明的探索入口？本期不承诺标签是真实性判定，也不启动 Claims2 分类后端重建。

## 四、测试怎么分工

“可立即做”表示不依赖新的客户材料，并不表示本轮已经执行完毕。

| 测试层 | 我们负责的检查 | 客户／材料负责人负责的输入或判断 | 留存的通过证据 |
|---|---|---|---|
| 网页与交互 | 页面导航、组合筛选、清空筛选、Unknown、空结果、导出、手机显示、失效链接和异常提示 | 哪些任务最常用；是否能独立完成 | 固定用例的操作记录、预期与实际结果、问题清单 |
| 确定性统计 | 在固定源快照上独立对账；明细、图表、交叉表、CSV 的记录集合和合计一致 | 确认分母、计数和实体归并规则 | 全量 ID 集合与计数，不以图表计算结果互相证明 |
| 数据完整性 | 字段映射、缺失、重复、范围、导入幂等、重跑／更新；异常记录可追踪 | 正式数据、字典、导出范围和数据负责人 | 输入 manifest、导入报告、未解决记录与来源 |
| 记录与归档 | 正文／附件身份、原文与归档切换、缺文件提示、线上 PDF 与预览可用 | 已有 URL→正文／附件对应关系；争议身份裁决 | 原文／附件定位和身份核验，缺失显式记录 |
| 检索 | 在固定题目与范围下检查所需文章、支持段落和相关性；记录遗漏及不相关结果 | 真实问题、已知重要文章和可接受的替代证据 | 逐题来源命中、支持片段覆盖、遗漏原因；与生成评分分开 |
| 生成答案 | 检查引用存在、版本和偏移；运行受控的付费评价，保存失败、延迟、成本 | 领域人员判断答非所问、归属、必要限定、事实之外的推断和遗漏 | 逐题人工 verdict＋理由；“存在引文”不能自动通过 |
| 社交／跨库 | 接入后按两平台分别测试，再测跨库筛选、检索与重复计数 | 正式导出及平台字段语义 | 真实数据对账和相应题目结果；材料缺失记 blocked，不记 pass |
| 部署与运维 | 记录代码／数据／索引版本；验证持久化、备份恢复、重启、预算限制和故障恢复。恢复及压力检查先在隔离环境执行 | 项目／账户负责人确认维护人、预计用户规模、服务预算和访问范围 | 部署清单、恢复记录、实际负载／延迟及交接演练；不对生产随意重启或压测 |
| 用户验收 | 准备任务与反馈表，观察操作路径和障碍 | 领域负责人加 1–2 名目标用户参与首轮试用（建议安排） | 完成率、误解点、可用性意见及明确的验收决定 |

### 建议的验收规则，需要共同确认

- **确定性功能**：约定测试范围内，表格、图表和导出应完全对账；重复、未知值和分母符合已确认口径。
- **引用与归属**：发现错误来源、编造引文、跨版本错配或把广告承诺写成已证实结果，应修复并复测；不能用平均分抵消这类严重问题。
- **检索与回答质量**：先明确目标问题、支持证据和什么算充分，再商定可接受的遗漏／错误率。没有代表性样本前不预设“95% 准确率”。
- **完整性**：按实际覆盖报告通过、失败、未运行和材料阻塞。社交空库、低覆盖或大量拒答不能算作全功能通过。
- **性能与费用**：根据预计并发、可接受等待时间和费用上限建立目标，再测量；目前没有客户批准的数字。

## 五、用已有题库减少客户负担

1. 保留 `eval/development.jsonl` 的开发用途；继续改进的案例不当作独立验收证据。
2. 团队将 20 条 `acceptance.draft.jsonl` 转成可读题目和证据表；客户检查研究价值、关键限定和遗漏，而不需要读 JSON 或填 UUID。
3. 结合新提供的问题选择一组保留题；已经反复用于调参的问题及同文章案例明确列为回归。若要报告对新文章的泛化表现，须按文章／近重复组隔离。
4. 对可回答题先固定问题、筛选范围、必要证据和评分规则；无证据题也要确认是既定语料不足，而不只是一次搜索没找到。
5. 原生、社交、跨库分别冻结并记录版本。允许先验收原生部分，但不能把它写成完整双数据集验收。
6. 团队运行检索和生成、提供原文上下文；领域审阅者标“通过／需修改／证据不足”，争议由指定负责人裁决。用过的验收案例若用于改代码，应转入开发记录并补保留题。

客户题目模板（自由文本也可）：

```text
研究问题／实际任务：
关注的平台、媒体、公司或日期范围：
若已有，相关广告／帖子链接：
答案必须说明什么、哪些误解最不能接受：
审阅人：
```

## 六、沟通顺序与材料未到时的安排

- **第一次沟通只优先收四类材料**：社交正式导出与字典、统计口径、原文／归档映射、真实问题与审阅人。可直接使用[英文邮件草稿](../deliverables/client_review_request_20260924.en.md)。
- **团队会前准备**：原生功能演示、16 条 sponsor 来源队列、少量日期／重复歧义例子、客户可读的验收题草案。把技术排错留给团队。
- **讨论后记录**：每项决定、负责人、交付时间、公开展示范围，以及仍未知的事项。没有客户答复不自动按建议视为批准。
- **交接前再确认**：指定 GitHub 及项目权限、Railway 和 API 的维护责任、数据更新周期、预计访问量和运行预算。由管理员通过平台分配权限，技术版本记录由团队完成。
- **材料暂缺时继续推进**：原生功能回归、统计对账、错误状态、引用定位、归档候选核验、测试表和运维文档；对未接入社交／跨库如实标注阻塞。

原型参考入口需区分：本期需要的 Miami 社交仪表盘访问由 PM 向 Ned 协调；已有 Claims2 是另一套分类审核工具，不替代该原型或本期正式社交数据。
